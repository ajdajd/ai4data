# 3. Text classification

**Question:** How can text records be classified and reviewed using a defined set of categories?

## Rationale

Text classification assigns categories to whole pieces of text, such as
messages or survey responses. In a single-label project, each completed
record receives one category.

Doccano presents the allowed categories alongside each record. Written
labeling rules define when to use each category and how to flag uncertain
cases for review. This chapter covers project setup, manual classification,
and inspection of the native JSONL export.

## Target state

- Each text record has exactly one saved category under the labeling rules.
- Records that cannot be confidently classified remain visible for review.
- Native exports preserve source identifiers, unchanged text, and string-valued labels.

## Maturity levels

| Level | Steps |
|---|---|
| **Foundational** | A person assigns categories using written definitions and flags ambiguous records for review. |
| **AI-ready** | Stable identifiers and validated labels make the classified records reusable in downstream workflows. |
| **AI-native** | Reviewed labels can support the evaluation of automated classification. |

:::info[Running example]
The exercise uses statistical coding to assign occupation categories to six
fictional survey responses. It uses a subset of ISCO-08, the International
Labour Organization's occupation classification. The responses come from the
[Language Models in Production cookbook](/cookbook/language-models-in-production/coding)
and contain no real respondent data.
:::

## Recipes

<Recipe title="3.1 Set up a single-label coding project" level="Foundational" skills="Statistical coder or data practitioner comfortable with a terminal" time="Thirty minutes, plus dependency download time">

**Result:** Doccano contains six unlabeled responses in a single-label text-classification project.

A single-label project requires one category for a completed response. The
small codebook contains four ISCO-08 unit groups and a separate workflow
label for cases that cannot be assigned within this exercise. The input
records intentionally omit reference codes and model suggestions.

Doccano uses a web application for labeling and a worker for imports and
exports. Both must remain running while completing the exercise.

### Set up the dependencies

1. Create a working directory with folders for input files and exported
   annotations, then enter it.

```shell
mkdir -p annotation-codes/input annotation-codes/output
cd annotation-codes
```

2. Download [responses.jsonl](pathname:///cookbook-files/open-source-data-annotation/responses.jsonl)
   and [occupation-codebook.csv](pathname:///cookbook-files/open-source-data-annotation/occupation-codebook.csv)
   into `input`. Download
   [requirements-doccano.txt](pathname:///cookbook-files/open-source-data-annotation/requirements-doccano.txt)
   and [inspect_doccano.py](pathname:///cookbook-files/open-source-data-annotation/inspect_doccano.py)
   into the working directory. JSONL stores one JSON object per line; each
   input record represents one response with these fields.

| Field | Meaning |
|---|---|
| `source_id` | This stable response identifier connects the label back to the source record. |
| `dataset_id` | This field records the fictional survey round. |
| `text` | This field contains the unchanged occupation description. |
| `label` | The empty list is the native field for a response that has no assigned category yet. |

Inspect the input responses before importing them.

```json file=../../website/static/cookbook-files/open-source-data-annotation/responses.jsonl
```

3. Create an isolated Python 3.10 environment and install the supplied
   dependencies, including doccano 1.8.4. The `--override` option applies the
   compatibility versions in the requirements file. For platform-specific
   installation help, see the
   [official installation guide](https://doccano.github.io/doccano/install_and_upgrade_doccano/).

```shell
python3.10 -m venv .venv-doccano
source .venv-doccano/bin/activate
python -m pip install uv
uv pip install --python python -r requirements-doccano.txt --override requirements-doccano.txt
```

### Configure doccano

4. Create `.env` to set the local database and upload directory. Change
   `doccano-state` here to store the application state elsewhere.

```shell
cat > .env <<EOF
DOCCANO_HOME="$PWD/doccano-state"
EOF
```

5. Initialize the database and create the `annotator` account. Choose a password
   when prompted. These credentials are only for this local doccano instance.

```shell
dotenv -f .env run --no-override -- doccano init
read -rsp "Local annotator password: " DOCCANO_PASSWORD
dotenv -f .env run --no-override -- \
  doccano createuser --username annotator --password "$DOCCANO_PASSWORD"
unset DOCCANO_PASSWORD
```

6. Start the web application in this terminal.

```shell
dotenv -f .env run --no-override -- doccano webserver --port 8000 --workers 1
```

   In a second terminal, enter `annotation-codes`, activate the environment,
   and start the import/export worker. Leave both terminals running.

```shell
source .venv-doccano/bin/activate
dotenv -f .env run --no-override -- doccano task --concurrency 1
```

7. Open [http://127.0.0.1:8000](http://127.0.0.1:8000) and log in as `annotator`
   with the password from Step 5. On the project list, click **Create**.
   Name the project `Labour survey occupation coding` and choose
   **Text Classification**. Enable **Single label**, then save the project.
   Open **Labels** in the project menu and add the five values from the
   codebook's `code` column, including `NEEDS_REVIEW`. Use the exact values
   so that the exported labels can be checked against the codebook. For
   another classification task, replace these with the applicable categories.
8. Open **Dataset → Actions → Import Dataset**. Choose **JSONL** and select
   `input/responses.jsonl`. Set the text column to `text` and the label column
   to `label`, then import the file. Expect six records. Click
   **Start annotation** to open the first response. Its metadata should include
   `source_id: r01`, and the label list should offer the five codebook categories.

**Worked example.** The first record, `r01`, says “primary school teacher”.
After importing `input/responses.jsonl`, the annotation interface displays
that text with no category selected. The project offers `2341` and the other
four labels, ready for coding.

**What this does not do.** The project does not load the full ISCO hierarchy
or enforce the definitions of every occupation. This local exercise does not
configure a shared production deployment or a model suggestion service.

</Recipe>

<Recipe title="3.2 Assign occupation codes and review labels" level="Foundational" skills="Statistical coder with the teaching codebook" time="Twenty minutes">

**Result:** Each response has a supported occupation code or a visible NEEDS_REVIEW decision.

Use `input/occupation-codebook.csv` to decide which category matches the work
described. Its `code` column supplies the label value, `title` names the
category, and `teaching_rule` explains when to use it. `NEEDS_REVIEW` is a
local review status for responses that cannot be assigned to one of the four
occupation categories.

```csv file=../../website/static/cookbook-files/open-source-data-annotation/occupation-codebook.csv
```

1. In the annotation interface, find `source_id: r01` in the record metadata.
   Read “primary school teacher” and click `2341` in the category list. Expect
   one selected category. Click the review indicator (initially **×**) in
   the annotation toolbar. It should change to **✓**, marking the response
   as reviewed.
2. Use the navigation arrows to continue. Assign `8322` to `r02`, which
   describes driving a taxi, `5211` to `r03`, which describes selling
   vegetables at a market, and `7231` to `r06`, which describes repairing
   motorcycles. Confirm each response after labeling it.
3. Assign `NEEDS_REVIEW` to `r07`, “works in a shop”, and `r14`, “helps at
   home”. Neither response provides enough detail to support one of the four
   occupation categories. Confirm both responses; the review label keeps
   them visible for later follow-up.
4. To correct a category, click the supported label to replace the previous
   selection. Check that the review indicator shows **✓**, navigate away,
   and return to check that exactly one category remains selected.

**Worked example.** The teaching decisions are `r01 → 2341`, `r02 → 8322`,
`r03 → 5211`, and `r06 → 7231`. Records `r07` and `r14` remain
`NEEDS_REVIEW`. The next statistical processing step should retain those
review cases and exclude the workflow label from occupation counts.

**What this does not do.** A small codebook cannot cover a national survey.
Production coding needs the complete applicable classification, fuller
response context, and procedures for clarification and adjudication.

</Recipe>

<Recipe title="3.3 Export and verify native response labels" level="AI-ready" skills="Statistical coder; basic Python use" time="Fifteen minutes">

**Result:** Native doccano JSONL retains each response identifier and exactly one permitted string label.

The native JSONL representation keeps the response text beside its category
list. Even in a single-label project, `label` is a list such as `["2341"]`.
A stable source identifier allows the label to be joined to the source survey
record without relying on the application's internal IDs or row order.

1. Use **Actions → Export Dataset** and select **JSONL** for the complete
   reviewed set. Extract the archive if necessary and save the annotator's
   file in `output` as `codes-export.jsonl`. Keep the native file unchanged.
2. In a terminal in `annotation-codes`, run the inspection script. It prints
   each response identifier and its assigned category.

```shell
python inspect_doccano.py classification output/codes-export.jsonl \
  --source input/responses.jsonl \
  --codebook input/occupation-codebook.csv
```

The supplied [example export](pathname:///cookbook-files/open-source-data-annotation/codes-export.jsonl)
shows the expected assignments. With the same categories, the command prints:

```text
r01 2341
r02 8322
r03 5211
r06 7231
r07 NEEDS_REVIEW
r14 NEEDS_REVIEW
PASS: 6 unchanged record(s); 6 code(s).
```

The first path selects the export, `--source` selects the original responses,
and `--codebook` selects the allowed categories. Change these paths for other
files. The script rejects changed text, missing or duplicate identifiers,
numeric codes, unknown categories, and empty or multiple labels.

3. Compare the printed assignments with the categories saved in doccano.
   Open `output/codes-export.jsonl` in a text editor to inspect its fields.
   Keep the input responses and codebook with the export so that its labels
   remain interpretable.

| Field | What to inspect |
|---|---|
| `source_id` | The identifier connects the label to the original response, regardless of the tool's internal IDs or row order. |
| `text` | The response must match the input exactly. |
| `label` | The list contains exactly one quoted string, such as `["2341"]` or `["NEEDS_REVIEW"]`. Keeping codes as strings preserves leading zeros in larger codebooks. |

**Worked example.** A record containing `source_id: "r01"` and
`label: ["2341"]` can be joined back to response `r01`. The intended complete
export has six responses, four occupation-code assignments, and two review
assignments.

**What this does not do.** A structurally valid category can still be wrong.
The validator does not measure coder agreement, resolve review cases, or
certify the sample as a gold-standard dataset. No model assistance is included.

</Recipe>

## Implementation options

- Native JSONL preserves list-valued string labels and source metadata for inspection and later joins.
- Native CSV is an alternative when its label encoding and string types are checked before reuse.
- The full ISCO classification belongs in a production coding procedure; the small flat codebook is sufficient for learning the tool.

## Common mistakes

- A workplace description is treated as evidence of a specific occupation without enough detail about the work.
- Multiple categories remain selected because the project was configured as multilabel.
- A workflow review label is counted as a valid ISCO occupation code.
- Converting codes to numbers can remove leading zeros when the codebook grows.

## Verification

- Confirm that the project is configured for one category per completed response.
- Check all six source identifiers and unchanged responses in the native export.
- Compare category assignments with the codebook and retain both review cases.
- Save a corrected category, reopen the record, and confirm that exactly one category remains in the native export.
