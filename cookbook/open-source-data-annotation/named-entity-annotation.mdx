# 2. Named entity annotation

**Question:** How can entity mentions in text be marked and reviewed?

## Rationale

Named entity annotation marks references to people, places, organizations,
or other entities in text. For example, a curator can label organization
names across a collection of reports so readers can find reports that mention
a particular organization. Labeled examples can help train models to recognize
entity mentions beyond exact string matches and extract structured fields from
unstructured text. The extracted entities can supply nodes for knowledge graphs,
and their locations in the source text can help ground large language model outputs.

Using doccano, an annotator can highlight the exact text of each entity and
assign a label. The selected range of text is called a span. The native JSONL
export keeps the original text with each span's label and start and end
character positions. The positions let a reviewer recover the selected
text or check whether an automated extraction system finds the same mentions.

## Target state

- Every imported passage retains a stable source identifier and unchanged text.
- Entity spans follow written labeling rules and have been reviewed.
- The native JSONL export reconstructs the intended text from every span.

## Maturity levels

| Level | Steps |
|---|---|
| **Foundational** | A person marks entity mentions and checks the selected text in the export. |
| **AI-ready** | Stable identifiers and validated offsets make the labels reusable by software. |
| **AI-native** | A model could propose spans for human correction with provenance retained. This extension is outside this edition. |

The first three sentences are the core exercise. The remaining eleven are

## Recipes

<Recipe title="2.1 Set up a dataset-mention project" level="Foundational" skills="Data practitioner comfortable with a terminal and a browser" time="Thirty minutes, plus dependency download time">

**Result:** Doccano contains a sequence-labeling project with 14 unchanged sentences and one DATASET label.

Doccano uses a web application for labeling and a worker for imports and
exports. Both must remain running while completing the exercise.

### Set up the dependencies

1. Create a working directory with folders for the input passages and exported
   annotations, then enter it.

```shell
mkdir -p annotation-entities/input annotation-entities/output
cd annotation-entities
```

2. Download [passages.jsonl](pathname:///cookbook-files/open-source-data-annotation/passages.jsonl)
   into `input`. JSONL stores one JSON object per line.
   Inspect the UTF-8 input before importing it. Each record has these fields.

| Field | Meaning |
|---|---|
| `source_id` | This stable identifier distinguishes a passage, even when passages repeat a dataset name. |
| `document_id` | This field preserves the source sample's document identifier, D01–D06. |
| `text` | This exact text is displayed and labeled. |
| `label` | The empty list supplies the native annotation field without revealing any answers. |

The input contains 14 records, identified as `m01`–`m14`. Each starts with
an empty `label` list so that annotation begins without suggested answers.

```json file=../../website/static/cookbook-files/open-source-data-annotation/passages.jsonl
```

3. Create and activate an isolated Python 3.10 environment, then install
   doccano and the other packages listed below. This example uses `venv`
   and pip. For platform-specific installation help, see the
   [official installation guide](https://doccano.github.io/doccano/install_and_upgrade_doccano/).

```shell
python3.10 -m venv .venv-doccano
source .venv-doccano/bin/activate
python -m pip install --upgrade pip
python -m pip install "doccano==1.8.4" "python-dotenv[cli]>=1.1,<2" \
  "marshmallow==3.26.2" "numpy==1.26.4" "setuptools==80.9.0"
```

### Configure doccano

4. Create `.env` to set the local database and upload directory. Change
   `doccano-state` here to store the application state elsewhere.

```shell
cat > .env <<EOF
DOCCANO_HOME="$PWD/doccano-state"
EOF
```

5. Initialize the database and create the `annotator` account. Choose a password
   when prompted. These credentials are only for this local doccano instance.

```shell
dotenv -f .env run --no-override -- doccano init
read -rsp "Local annotator password: " DOCCANO_PASSWORD
dotenv -f .env run --no-override -- \
  doccano createuser --username annotator --password "$DOCCANO_PASSWORD"
unset DOCCANO_PASSWORD
```

6. Start the web application and import/export worker in the background.
   Keep this terminal open for the rest of the exercise.

```shell
dotenv -f .env run --no-override -- doccano webserver --port 8000 --workers 1 \
  >/dev/null 2>&1 &
doccano_web_pid=$!
dotenv -f .env run --no-override -- doccano task --concurrency 1 \
  >/dev/null 2>&1 &
doccano_worker_pid=$!
```

7. Open [http://127.0.0.1:8000](http://127.0.0.1:8000) and log in as `annotator`
   with the password from Step 5.
8. On the project list, click **Create**.
   Choose **Sequence Labeling** and name the project `Data Use sentence annotation`.
   Add the project description `Sample exercise`. Leave other settings unchecked,
   then save the project.
9. Open **Labels** in the project menu. Click **Actions** then select **Create Label**. Add `DATASET`
   then click **Save**. For another use case, choose the label names
   that describe the entities to mark.
10. Open **Dataset → Actions → Import Dataset**. Choose **JSONL** and import
   `input/passages.jsonl`. Set the text column to `text` and the label column
   to `label`, then import the file. Expect 14 records.
11. In the **Dataset** table, find the row with `"source_id": "m01"` in the
    **Metadata** column. Click **Annotate** on that row. Check that the
    annotation view shows `m01` and offers the `DATASET` label.

After finishing Recipes 2.2 and 2.3 and any optional checks, stop the
web application and worker from the same terminal.

```shell
kill "$doccano_web_pid" "$doccano_worker_pid"
wait "$doccano_web_pid" "$doccano_worker_pid"
```

**Worked example.** Record `m01` contains “We use the Household Budget
Survey 2021 to estimate consumption per adult equivalent.” Record `m14`
contains “The outlook covers twelve countries in the region.” Importing
`input/passages.jsonl` puts both in the project without highlighted words,
ready for annotation.

**What this does not do.** This local setup does not configure a shared
production service, optical character recognition (OCR), or PDF text
extraction. The passages are prepared inputs. The application must not
transform them after span positions are set.

</Recipe>

<Recipe title="2.2 Label dataset mentions" level="Foundational" skills="Data curator or research annotator" time="Ten minutes for the three required passages">

**Result:** The first three passages each have one saved and reviewed `DATASET` span.

For this exercise, `DATASET` marks a specific source of data: a survey,
census, indicator series, or report. The source may be named or described.
A generic phrase such as “a food security report” receives no label.

1. In the annotation interface, find `source_id: m01` in the record metadata.
   Drag across `Household Budget Survey 2021` in the sentence, then choose
   `DATASET` from the label menu. Click the **×** button in the toolbar
   and confirm it changes from **×** to **✓** to save the annotation.
2. Use the next arrow to open `m02`. Label `HBS` as `DATASET` and save the annotation.
3. Continue to `m03`. Label `prevalence of undernourishment series` as
   `DATASET` and save.

To correct a selection, right-click the highlight to remove it. Select the
intended text, apply `DATASET` again, and confirm the correction.

**Optional practice.** Continue in order through `m04`–`m14`. Label and
save `m04`–`m12`. For `m13` and `m14`, save each without adding a highlight.

**Worked example.** After `m03`, three spans have been saved and reviewed. In
the third sentence, the word `official` and the final period fall outside the
selected span.

**What this does not do.** This exercise does not resolve every descriptive
or vague reference in research literature. Difficult cases need a documented
annotation decision and possibly a second reviewer. Repeated names at
different positions remain separate mentions.

</Recipe>

<Recipe title="2.3 Export and verify native entity spans" level="AI-ready" skills="Data curator; basic Python use" time="Fifteen minutes">

**Result:** A native doccano JSONL export preserves the original passages and reconstructs every selected mention.

The export stores selected words as character positions, called offsets.
The inspection script displays the words at those positions and checks that
the exported sentences still match the input.

1. In the sidebar, go to **Dataset**. Use **Actions → Export Dataset** and choose **JSONL**. Leave **Export only approved documents** unchecked to include all 14 records. Click **Export**.
2. Extract the download archive and save the
   annotator's JSONL in `output` as `entities-export.jsonl`. Keep the native file unchanged, including its metadata.
3. Download [inspect_doccano.py](pathname:///cookbook-files/open-source-data-annotation/inspect_doccano.py)
   into `annotation-entities`. In the same terminal, run the script to display
   each selected phrase on its own line.

```shell
python inspect_doccano.py entities output/entities-export.jsonl \
  --source input/passages.jsonl
```

For the three required annotations, expect the following output.

```text
m01 [11:39] 'Household Budget Survey 2021'
m02 [4:7] 'HBS'
m03 [47:84] 'prevalence of undernourishment series'
PASS: 14 unchanged record(s); 3 span(s).
```

The [full example export](pathname:///cookbook-files/open-source-data-annotation/entities-export.jsonl)
includes the optional annotations, for a total of 12 spans.

The first path selects the export to inspect; `--source` selects the original
input. Change these paths when using other files. The script rejects changed
text, missing or duplicate source identifiers, invalid offsets, unknown labels,
and overlapping spans.

4. Compare the displayed phrases with the highlights saved in doccano.
   Open `output/entities-export.jsonl` in a text editor to inspect a record's
   fields. Keep `input/passages.jsonl` with the export so that its offsets can
   always be checked against the original text.

| Field | What to inspect |
|---|---|
| `source_id` | The identifier connects each annotation to its input sentence, regardless of the tool's internal record ID. |
| `text` | The sentence must match the input exactly. |
| `label` | Each selection has the form `[start, end, "DATASET"]`. The start is included and the end is excluded. Positions count Unicode code points. |

**Worked example.** A native label triple `[11, 39, "DATASET"]` for `m01`
reconstructs `Household Budget Survey 2021`, the phrase selected in Recipe 2.2.
The export contains the same 14 source identifiers, including `m13` and `m14`
with no entity labels.

**What this does not do.** Valid offsets can still select the wrong words.
An empty label list does not prove that a person reviewed the record. The
validator does not normalize text, align changed versions, or measure model
quality. Relation-enabled exports are outside this introductory format.

</Recipe>

## Implementation options

- Native JSONL preserves text and character offsets without an intermediary annotation schema.
- The official container setup is an alternative to the isolated Python installation.
- A named entity recognition model such as [GLiNER2](https://arxiv.org/abs/2507.18546) could propose dataset-mention spans for human correction in doccano. Predictions would need to follow the DATASET policy and preserve the exact input text and offset convention. Model inference and pre-annotation import are outside this edition.

## Common mistakes
- Treating generic data nouns as named datasets changes the agreed inclusion policy.
- Deduplicating repeated names removes separate mention positions that the annotation task needs.
- Replacing source identifiers with internal project IDs breaks the connection to the original passages.
- Changing text after annotation can shift span offsets even when the text
  looks the same. Apply any needed Unicode normalization or whitespace cleanup
  before import, then preserve the exact text through export. In Python,
  `text[start:end]` should reproduce the highlighted text.
