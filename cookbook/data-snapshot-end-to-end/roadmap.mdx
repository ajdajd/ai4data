# 8. Extraction improvements and future models

**Question:** What should improve next and how should changes be assessed?

## Rationale

The production pipeline is a useful baseline for producing candidate crops and semantic descriptions. The Shona example shows two gaps directly: layout classes admit a decorative photograph, and detected boxes can exclude captions. Neither more detailed metadata nor a larger output budget fixes the first-stage evidence boundary.

The following roadmap is proposed work. It separates filtering candidates, improving boundaries, and assessing metadata so that a gain in one area is not mistaken for a complete solution. Human review remains necessary when defining analytical relevance and judging borderline artifacts.

## Target state

- A proposed second-stage classifier has an explicit purpose and evaluation boundary.
- Future detector and metadata updates have evidence-based acceptance criteria.

## Maturity levels

| Level | Steps |
|---|---|
| **Foundational** | A curator inspects the source page and records the evidence and unresolved questions. |
| **AI-ready** | A developer runs the documented stage and checks its files against the source and schema. |
| **AI-native** | The organization proposes monitored automation with retained evidence and human review. This level describes an operational goal. The available package features are documented separately. |

This chapter uses the Shona policy brief and the figure and table on PDF page 4. The recorded exercise uses snapshot-only extraction and metadata-only requests for these two crops. Combined execution is an unexecuted illustration.

## Recipes

<Recipe title="8.1 Design a second-stage analytical relevance classifier" level="AI-native" skills="Developer and data curator" time="Twenty minutes plus execution and review">

**Result:** The organization has a reviewable proposal for filtering irrelevant candidate crops.

A second-stage classifier would examine regions proposed by the layout detector and predict whether they contain analytically useful information. It would sit between cropping and paid metadata generation. It is not implemented in the production package or invoked by any command in this guide.

1. Collect reviewed positive and negative candidates across institutional document types. Include charts, statistical and financing tables, maps, composites, photographs, logos, tables of contents, and formatting grids. Keep ambiguous cases for adjudication.
2. Split development and evaluation data by source document to reduce leakage between related crops. Record inclusion rules and label provenance.
3. Compare a small image classifier or vision-language classifier with the unfiltered detector baseline. Tune a rejection threshold on development data and retain uncertain cases for human review.
4. Measure precision gain, analytical snapshots incorrectly rejected, overall recall after both stages, latency, and downstream request volume on held-out documents. Fix the acceptable recall loss before evaluating the final candidate.

**Worked example.** The cover photograph is a candidate negative, while the selected chart and demographic table are candidate positives. These three examples explain the decision but do not form a training or validation set. No accuracy improvement is claimed.

**What this does not do.** A classifier cannot recover missed regions or restore an omitted caption. Adding a second stage can reduce recall and has its own compute and maintenance cost.

</Recipe>

<Recipe title="8.2 Gate pipeline and model updates on reviewed evidence" level="AI-native" skills="Developer and data curator" time="Twenty minutes plus execution and review">

**Result:** A proposed update has a bounded test and a recorded acceptance decision.

Model releases and better academic benchmark results motivate investigation. Replacing a tested institutional workflow requires local evidence. The organization needs evaluation evidence connected to its document types and to the use of the final crops.

| Priority | Proposed change | Evidence needed before adoption |
|---|---|---|
| Candidate relevance | Add the second-stage classifier. | Held-out precision and overall recall, with rejected analytical artifacts reviewed. |
| Boundary completeness | Include detached captions and notes; handle composites. | Reviewed page boxes and measures of captured context and unrelated surrounding area. |
| Source linkage | Consider retaining page and box information when scaling beyond the exercise. | A documented output contract and tests linking crops to source pages. |
| Metadata quality | Compare compatible image models and prompts. | Schema validation plus field-level human review of accuracy, omissions, and unsupported content. |
| Operations | Add failure reporting, controlled retries, and request accounting. | Output-preservation tests, request limits, and reproducible recovery demonstrations. |

1. Keep the current example and a broader reviewed institutional sample as regression cases.
2. Test a proposed detector with its required dependency environment, hardware, model licence and image settings. Compare misses, false positives, fragmented composites, captions, and notes.
3. Test metadata changes on fixed crops so that detector changes do not confound model comparison. Preserve prompts, presets, and raw responses where permitted.
4. Publish the decision and unresolved failures alongside the candidate results. Adopt only when the agreed gates pass; otherwise retain the tested baseline.

**Worked example.** A future update should explain whether it rejects the Shona photograph and preserves the chart and table captions, then show performance on additional held-out documents. The two illustrated problems define concrete checks without establishing a general benchmark.

**What this does not do.** The roadmap adds no classifier, crop-repair algorithm, retry service, numerical transcription, or publication integration in this contribution.

</Recipe>

## Implementation options

The separate experimental package provides research annotation and evaluation workflows. The production adapters provide a canonical `Detection` contract for model integration. Proposed improvements should be implemented and tested separately from the cookbook's recorded outputs; links to the production README and schema reference remain the technical authorities.

## Common mistakes

- Training on the same crops used to report performance overstates improvement.
- Reporting classifier precision alone hides lost analytical snapshots.
- Changing detector and metadata model together obscures the source of a quality change.

## Verification

- The classifier is explicitly proposed and unimplemented.
- Evaluation separates relevance, boundaries, metadata quality, and operational safety.
- Future updates require held-out evidence and recorded human decisions.
