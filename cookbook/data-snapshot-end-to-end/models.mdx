# 7. Model selection and tradeoffs

**Question:** Which detector, device, and metadata model fit the task?

## Rationale

Detection and metadata extraction answer different questions. A layout detector proposes where a figure or table lies; a metadata model describes what is visible inside its data snapshot. A strong description cannot recover a title or footnote that detection excluded. Selecting each stage therefore requires reviewing its own failure modes.

The worked example uses DocLayout-YOLO on CPU and the existing OpenRouter metadata preset. No alternative detector or model is needed to complete the initial workflow. The recipes establish those settings first, then explain the optional choices for a different runtime or provider. Later changes should be assessed on the organization's documents, including the review burden created by irrelevant or incomplete data snapshots.

## Target state

- The detector and inference device are explicitly chosen.
- The metadata preset and its compatibility assumptions are documented.

## Maturity levels

| Level | Steps |
|---|---|
| **Foundational** | The organization chooses a detector, device, and metadata provider for one document and notes the settings used. |
| **AI-ready** | Developers share documented configurations, check runtime and provider compatibility, and assess output quality before changing the selected models. |
| **AI-native** | An organizational process monitors model-assisted output and proposes configuration changes for human review against agreed quality criteria. Such monitoring is additional integration work. |

:::info[Running example]
The recorded workflow for the sample PDF used in the tutorial uses DocLayout-YOLO on CPU and the unchanged packaged OpenRouter metadata preset. These are the settings used in the preceding extraction and metadata examples. Alternative detectors, GPU devices, and provider settings are optional paths; they were not evaluated for this example.
:::

## Recipes

<Recipe title="7.1 Select a detector and inference device" level="AI-ready" skills="Developer and data curator" time="Ten minutes to confirm the default detector and device">

**Result:** The extraction command names a supported detector and a device available on the machine.

The installation in [chapter 1](./preparation.mdx) supplies the default detector. The arguments `--model=doclayoutyolo --device=cpu` select DocLayout-YOLO and local CPU inference. The detector proposes candidate regions; its confidence score does not establish whether each data snapshot is analytically useful.

1. Keep `doclayoutyolo` as the detector for the initial workflow so that the commands match the recorded example.
2. Keep `cpu` as the device. This avoids assuming that a compatible GPU and runtime are available.
3. Review the outputs from [snapshot extraction](./snapshots.mdx) before trying the optional choices below.

**Worked example.** The recorded exercise used DocLayout-YOLO on CPU. It saved seven figure-labelled candidate images and one table-labelled candidate image, including a cover photograph. [Chapter 2](./snapshots.mdx) identifies the chart and table selected from that candidate set. Other detector and device choices were not evaluated for this guide.

<details>
<summary>Optional detectors and GPU devices</summary>

The supported detectors use different optional dependencies. The table identifies the relevant extra and the settings supplied by the package.

| Detector | Extra | Practical consideration |
|---|---|---|
| `doclayoutyolo` | `data-snapshot` | The recorded baseline uses 1024-pixel inference and a confidence threshold of 0.2. Captions can fall outside its boxes. |
| `yolo11` | `data-snapshot-yolo11` | The packaged medium model uses 1280-pixel inference. Its outputs still need review against the source pages. |
| `yolo26` | `data-snapshot-yolo26` | This medium layout model also uses 1280-pixel inference. Its release date alone does not establish suitability for an institution's documents. |
| `tfid` | `data-snapshot-tfid` | This detector uses an older Transformers stack and model-provided code at a configured revision. It requires a separate environment. |

1. To try YOLO11, install `python -m pip install ".[data-snapshot-yolo11]"` and select `--model=yolo11`. YOLO26 uses the corresponding `data-snapshot-yolo26` extra and `--model=yolo26`.
2. Install TF-ID in its own environment with `python -m pip install ".[data-snapshot-tfid]"`, then select `--model=tfid`. Add `data-snapshot-metadata` there only if metadata extraction is needed. Do not combine this stack with `all`.
3. Select `--device=cuda:0` only when the installed runtime and hardware support that CUDA device. An unavailable device is an error; the workflow does not automatically fall back to CPU.
4. Use a fresh output root for an optional trial so that existing files are preserved and do not trigger skip logic. The Python APIs `run_extraction` and `run_pipeline` also accept `device="cuda:0"`.

Device selection controls local PDF detection. Remote metadata inference uses the provider's infrastructure. The [benchmark paper](https://arxiv.org/html/2606.06242v1) provides historical evaluation for readers investigating detector choices; this cookbook adds no alternative-model demonstration.

</details>

**What this does not do.** The CLI does not expose the confidence threshold, minimum bounding-box area, overlap threshold for duplicate suppression, or inference image size. The overlap threshold uses intersection-over-union (IoU), which divides the area shared by two boxes by the area of their union. Duplicate suppression uses this measure to reduce overlapping detections. These are detector adapter configuration settings in Python. No speed or accuracy ranking is inferred from this one PDF.

</Recipe>

<Recipe title="7.2 Confirm the metadata preset and configure alternatives" level="AI-ready" skills="Developer and data curator" time="Fifteen minutes to inspect the preset; changes require additional compatibility checks">

**Result:** The selected provider preset names the intended model and compatible request settings.

A metadata preset is a packaged JSON configuration that names the provider, model, and request settings. For the default path, keep the OpenRouter preset unchanged and use `--metadata-provider=openrouter` in the metadata commands. The environment needs `OPENROUTER_API_KEY`, as described in [chapter 1](./preparation.mdx).

Metadata presets are separate from `config/models.json`, which holds detector weight locations. The CLI selects a packaged provider preset and has no metadata `--model` or `--config` option. These distinctions matter when an organization later changes its metadata model.

1. Inspect `src/ai4data/data_snapshot/metadata_extraction/config/openrouter.json` in the checkout and confirm that it is the preset intended for the example.
2. Keep its model and request settings unchanged for the initial workflow. The configuration below shows the default production preset.
3. Compare these settings with the separate extraction stages in [chapter 2](./snapshots.mdx) and [chapter 3](./metadata.mdx). Optional provider and model changes are described in the collapsible section below.

The current OpenRouter preset is embedded from the production file:

```json file=../../src/ai4data/data_snapshot/metadata_extraction/config/openrouter.json
```

<details>
<summary>Optional provider and metadata model changes</summary>

A different model must accept image input through the selected provider's Responses API and support strict structured output. Request settings that work for one model may be unsupported by another.

The OpenAI alternative is also a packaged preset:

```json file=../../src/ai4data/data_snapshot/metadata_extraction/config/openai.json
```

1. Open `src/ai4data/data_snapshot/metadata_extraction/config/openrouter.json` or `openai.json` in the source checkout, according to the intended provider. Select OpenAI with `--metadata-provider=openai` and configure `OPENAI_API_KEY`.
2. Edit the `model` value to the intended compatible model. OpenRouter identifiers include their provider prefix. Keep `provider` consistent with the endpoint.
3. Review `max_output_tokens`, `timeout`, `reasoning`, and `service_tier` for that model. Unsupported settings can make the request fail. The output-token limit is not a total spending cap; `timeout` limits waiting time.
4. Reinstall the checkout after edits using the installation command in [chapter 1](./preparation.mdx). An editable contributor installation, `python -m pip install -e ".[data-snapshot,data-snapshot-metadata]"`, makes source edits effective immediately. Changes to installed configuration can be replaced during upgrades.

</details>

**Worked example.** The selected requests use the unchanged OpenRouter preset. Larger output allowances may avoid truncation for complex records but can permit more output tokens; model quality, latency, price, and schema adherence require assessment on reviewed data snapshots.

**What this does not do.** Selecting or editing a preset does not change the metadata schema or prompt contract. It provides no universal model recommendation and makes no provider-price claim. Automatic retries are disabled.

</Recipe>

## Implementation options

Detector locations resolve from explicit Python configuration, then `AI4DATA_SNAPSHOT_<MODEL>_*` environment overrides, then packaged defaults. A working-directory `.env` is loaded by the PDF commands. GPU settings are passed through `--device`; metadata inference runs at the external provider.

## Common mistakes

- Treating detector confidence as a probability of analytical usefulness can admit decorative content.
- Changing a metadata model without checking its supported request settings can cause failures.
- Increasing DPI cannot restore information missing from the original scan.

## Verification

- Inspect the planned extraction command. The default example should select `--model=doclayoutyolo --device=cpu`, matching the dependencies installed in chapter 1.
- Inspect the selected metadata preset and credential name. The default path uses the packaged OpenRouter configuration and `OPENROUTER_API_KEY`; no model edit is needed to follow the example.
- If an alternative is chosen, check its extra, runtime, device, and provider requirements before proceeding. A proposed configuration change is not evidence of a successful run.
